# 备选协议端调研：Tata / LLBot / SnowLuma

> 调研日期：2026-09-19 ｜ 背景：NapCat 4.15.0 回退观察期，评估是否有更优替代方案
> 结论先行：**没有发现值得立即迁移的理由**，SnowLuma 值得放入观察名单，LLBot 备选，"Tata"查无此框架。

---

## 一、Tata —— 查无此框架 ⚠

- 联网多轮检索（"Tata QQ机器人框架"、NTQQ 协议端、GitHub），**不存在叫 "Tata" 的 QQ 机器人协议端/框架**。
- 最接近的只是 **TataruBot2（塔塔露）**：一个 FF14 主题的机器人应用，基于 **go-cqhttp + NoneBot2** 搭建——go-cqhttp 已停止维护且 Android 协议基本失效，无参考价值。
- 可能性：名字记串了（Tata ↔ Tataru？Taichi？）或某个极小众项目。**建议提供来源（GitHub 链接/群聊截图）**，我再核实。

## 二、LLBot（LuckyLilliaBot，前身 LLOneBot）

| 维度 | 情况 |
|---|---|
| 定位 | OneBot 服务端（协议端），前身是 LiteLoaderQQNT 插件，现基于 **PMHQ**（内存注入 NTQQ） |
| 协议 | OneBot 11 + Satori + Milky 三协议 |
| 形态 | Desktop（要挂真实 QQ 客户端）/ CLI / Docker 多版本 |
| 热度 | GitHub 3.5k star，社区活跃（Telegram + QQ 群） |
| 生态 | 可对接 NoneBot2（我们现有机器人层可直接对接 ✅） |

**优点**：多协议、可视化 WebUI、生态兼容 NoneBot2；服务器直连模式性能尚可。
**风险/劣势**：
- 社区已有"**LLBot 跑路了**"的传言（linux.do 2026-06 帖子，后经澄清作者只是暂失联，但反映维护不确定性）；
- 用户反馈"用 llbot 和 napcat 老是被踢下线"——**风控表现与 NapCat 同级**，没有证据更好；
- Desktop 形态依赖有头 QQ，服务器部署不如 NapCat Shell 干净。

**结论：备选。没有比 NapCat 更稳的证据，迁移收益不明确。**

## 三、SnowLuma —— 上升期新星，最值得跟踪 ⭐

| 维度 | 情况 |
|---|---|
| 定位 | 独立 OneBot v11 协议端（自带 Node.js 运行时，不依赖系统 QQNT 客户端），附 WebUI/SDK/MCP |
| 原理 | 解析 QQ 客户端流量、映射身份，转成 OneBot v11 JSON；多账号会话隔离 |
| 热度 | 2025-06 创建，**近 30 天 +767 star（目前约 1.1k），正在趋势榜上升期** |
| 与 NapCat 关系 | **NapCat 作者参与了 SnowLuma 开发**；NapCat 官方 README 推荐它作为 GUI 替代品 |
| 风控口碑 | 社区实证（linux.do）："之前用 llbot 和 napcat 老是被踢下线，**换了这个就再也没掉过**"——目前唯一的"比 NapCat 更稳"的一手反馈 |
| 限制 | ① **非 OSI 开源**：源码可见但非商业许可，核心 native 组件闭源；② 声明"仅供学习研究，与腾讯无关"；③ 项目仅 1 年历史，长期维护未知；④ 自动安装目前仅 Windows x64 |

**结论：观察名单第一名。** 它是目前唯一有"比 NapCat 不容易被踢"实证声音的方案，且有 NapCat 核心人员背书；但闭源 + 非商业许可 + 年轻，不宜现在就把生产切过去。

## 四、对照：我们现在的 NapCat 4.15.0

- NapCat 本体**仍在活跃更新**（2026-09 还有提交，10.6k star，是社区绝对主流）；
- 我们的痛点（被踢）已通过**版本回退（4.15.0）+ 养号**应对，假在线已有看门狗自愈兜底；
- 迁移 LLBot 需要重新处理服务器部署/看门狗适配，迁移 SnowLuma 还要接受闭源组件——**在 4.15.0 观察期出结果前，动协议端属于无谓风险**。

## 五、行动建议（按优先级）

1. **继续观察期**（3~5 天）：看 4.15.0 的被踢频率是否真的下降——这是决定要不要折腾的依据；
2. **第一优先级仍是换养过的实名老号**：所有社区反馈都指向"账号质量 > 框架选择"，哪怕换框架，老号问题不解决照样被踢；
3. **SnowLuma 挂观察名单**：每 2~4 周回访一次它的 star 趋势 / issue 风控讨论 / NapCat 社区口碑；若观察期内 4.15.0 仍频繁被踢，可在**非生产环境**试装 SnowLuma 做对比实测；
4. **LLBot 不主动考虑**：无风控优势证据 + 维护不确定性传言；
5. 换任何协议端前，先确认它支持 OneBot v11 反向 WS（我们 NoneBot 层可零改动对接——LLBot/SnowLuma 都满足）。

# 附：SnowLuma 迁移评估与试点方案（2026-09-19 制定，观察期后视结果执行）

> 决策背景：用户拍板"先设计方案计划，再观察两天，实在不行就换"。
> 兼容性结论（已核实）：SnowLuma 支持**反向 WebSocket**（WebUI 配置 WebSocket 客户端 → `ws://127.0.0.1:8080/onebot/v11/ws/`），与现 NapCat → NoneBot 链路同构；HTTP API 默认同为 3000 端口 + token。**NoneBot 层与 7 个业务插件零改动。**

## 0. 触发条件（什么时候真的换）

观察期（至 2026-09-21 前后）满足**任一**条即启动迁移：
- 4.15.0 出现 ≥3 次 KickedOffLine（服务端踢下线）；
- 假在线发作 ≥3 次/天（看门狗自愈正常但频繁，说明会话质量差）；
- 出现验证实名、冻结警告等升级风控信号。

反之若两天平稳，SnowLuma 转为"长期观察名单"，每 2~4 周回访，不动生产。

## 1. Phase 1：本地试点（约 1 天，不碰服务器、不占机器人小号）

**环境**：本地 Windows 电脑 + 备用小号（绝不同号双跑，避免互踢污染观察）。

1. 下载 `SnowLuma-v-win-x64.zip`（完整版自带 Node 运行时）→ 解压 → `launcher.bat`；
2. WebUI（localhost:5099）按引导：同意条款 → 接入 QQ 进程 → 备用小号扫码；
3. 配反向 WS 指向本地起的 NoneBot（可直接跑我们项目 venv + bot.py）。

**必测清单**（每项记录结果，决定 Phase 2 工作量）：

| # | 测试项 | 判定标准 |
|---|---|---|
| 1 | `/ping`、`/菜单`、群管命令全链路 | 全部正常响应 |
| 2 | **HTTP API 兼容**：`get_login_info`/`send_private_msg` 打 3000 端口 | 返回格式与 NapCat 一致（看门狗探针零改动的关键）|
| 3 | **假在线表现**：挂 24h+，观察是否出现 1006514/收发断 | 记录频次，与 4.15.0 对比 |
| 4 | **被踢表现**：被踢时日志输出什么文案、有无二维码文件、路径在哪 | 直接决定看门狗 FAIL_PATTERNS/QR_PATTERNS 怎么配 |
| 5 | **自动重登能力**：被踢后重启 SnowLuma，能否免扫码恢复 | 决定看门狗重登策略是否成立（最关键项）|
| 6 | 进程模型：进程名/启动命令/日志文件路径 | 决定进程守护与日志扫描改造点 |
| 7 | HTTP 探针 15s 超时行为：假在线深僵死时接口是否挂起 | 决定 PROBE_NONE 兜底是否同样适用 |

## 2. Phase 2：套件改造（约 1~2 天，全部本地进行）

设计原则：**协议端类型做成配置项**，不硬切——`部署配置.json` 新增：

```jsonc
"protocol_side": "napcat",   // 可选 "snowluma"；回滚 = 改回一行配置
```

改造点（watchdog.py / deploy.py）：

1. **进程守护**：`napcat_paths()`/`napcat_pids()` 按 protocol_side 分派（SnowLuma：launcher 进程 + 路径探测）；
2. **日志扫描**：OK_PATTERNS / FAIL_PATTERNS / QR_PATTERNS 按 Phase 1 实测文案配置化（挪进 部署配置.json，换端不改代码）；
3. **二维码同步**：SnowLuma 的二维码来源路径接入现有 `需要扫码登录.png` 同步逻辑；
4. **快速登录**：Phase 1 第 5 项若通过 → 重启即重登；不通过 → 看门狗降级策略（自动拉起 + 立即告警"需人工扫码"，邮件/提醒兜底）;
5. **deploy.py**：write 配置、目录探测、部署脚本支持 SnowLuma 的安装包结构；
6. 沙箱全量回归（沿用现有测试方法：probe 失败累积、跳变清零、give_up 等 3 场景 + 新增 SnowLuma 模拟）。

## 3. Phase 3：服务器切换与回滚（半天，SSH 远程可完成）

**切换步骤**：
1. 服务器下载 SnowLuma → WebUI 扫码（机器人小号，此时 NapCat 已停，同号不冲突）；
2. 配反向 WS + HTTP API（对齐现 8080/3000）；`部署配置.json` 改 `"protocol_side": "snowluma"`；
3. 重启看门狗 → 验证三件套：看门狗"已登录 ✅"、`/ping` 通、心跳自检消息正常；
4. NapCat 4.15.0 目录**原样保留**（不删），随时可回。

**回滚**（30 秒）：改回 `"protocol_side": "napcat"` → 重启看门狗 → NapCat 快速登录（凭据未过期时免扫码）。

## 4. 风险与红线

- 🔴 **账号安全**：换框架 = 登录环境突变，可能触发一次设备验证/实名核验，属预期现象，非事故；
- 🔴 **闭源组件**：SnowLuma native 部分不可审计，仅用于群管场景、不给它任何服务器敏感权限（不动防火墙、不加系统服务）；
- 🟡 项目仅 1 年：迁移后保留 NapCat 完整备份，社区若爆雷可秒回滚；
- 🟡 观察期数据对比基线：回退前 4.18.28 = 1.5h 被踢一次；4.15.0 数据以这两天实测为准，作为换/不换的最终依据。

## 决策落地记录（2026-09-20）

**最终路线：SnowLuma 只作协议端，群管业务继续用原 NoneBot 框架（零重写）。**

理由：

1. SnowLuma 输出**标准 OneBot v11**（HTTP / WS 与 NapCat 口径一致）→ 原业务框架可直接连，**所有群管功能一行代码都不用改**
2. 被风控识别的是**协议端指纹**（NapCat），不是业务框架；换协议端即可拿到"少被踢"的收益
3. AstrBot 路线的代价：11 个群管插件要按 AstrBot 的插件体系整体重写，收益与成本不成比例 → 放弃（其目录保留为闲置参考）

**据此确定的项目边界（必须遵守）：**

| 项 | 本项目（SnowLuma + NoneBot） | 原项目（NapCat + NoneBot） |
|---|---|---|
| 目录 | `D:\Desktop\QQ机器人-SnowLuma-NoneBot\` | `D:\Desktop\QQ群管机器人\` |
| 协议端 | SnowLuma（hook 桌面 QQ） | NapCat |
| 业务框架副本 | 本目录内 `qq-group-bot\` | 原目录内 `qq-group-bot\` |
| 业务端口 | 8081 | 8080 |
| 登录账号 | 小号（示例 1000000001） | 主号（示例 2000000002） |
| 关系 | 两个独立项目，各自演进，不共享进程与端口 | 保持可用，随时回滚 |
