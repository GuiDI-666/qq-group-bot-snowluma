# 部署说明（SnowLuma + NoneBot 版）

> 本项目是**独立项目**，与「QQ群管机器人」（NapCat 版）互不干涉。
> 全程不需要科学上网工具；Python 依赖走国内镜像，SnowLuma 提供加速镜像下载途径。

## 0. 前置条件

| 组件 | 要求 | 说明 |
|---|---|---|
| Windows | 10 / 11 / Server | 本机或服务器均可 |
| 桌面版 QQ（NTQQ） | 必须安装并**保持登录** | SnowLuma 通过 hook 注入正在运行的 `QQ.exe`；**版本需与 SnowLuma 对齐** |
| Python | 3.9 ~ 3.13 | 业务框架运行环境；`一键部署-SnowLuma版.bat` 会自动探测 |
| Node.js | **不需要** | SnowLuma 完整版自带 |

两条容易被忽略的硬性要求：

1. **版本匹配**：SnowLuma 的 native hook 是按 QQ 版本对齐的，QQ 自动升级到未适配的新版本会导致 hook 加载失败。用 `自检-SnowLuma版.bat` 可以看到"已安装版本 vs 对齐版本"。建议在 QQ 设置里关闭自动更新。
2. **同用户同权限**：SnowLuma 与 QQ 必须用同一个 Windows 用户、同样的权限级别（都用管理员或都不用），否则注入静默失败。

## 1. 一键部署

双击 **`一键部署-SnowLuma版.bat`**，它会依次完成：

1. 准备 Python 环境：优先复用项目 `venv\`，缺失则自动建 venv 并安装 nonebot 依赖（阿里云镜像 → 官方源自动回落）
2. 解压 SnowLuma 发行包到 `SnowLuma\`（兼容"包内带顶层文件夹"和"包内直接是本体"两种布局，旧目录自动改名备份）
3. 写入 OneBot v11 网络配置 `SnowLuma\config\onebot_<目标账号>.json`：
   - HTTP 服务端 `127.0.0.1:3100`
   - WS 服务端 `127.0.0.1:3001`
   - WS 客户端 → `ws://127.0.0.1:8081/onebot/v11/ws`（连本项目业务框架）
4. 体检：确认 `node.exe`、hook 组件齐全

**如果项目里没有 SnowLuma 发行包**，脚本会打印下载地址，手动下载后放到本项目根目录再重跑即可：

| 途径 | 地址 |
|---|---|
| GitHub 直连 | https://github.com/SnowLuma/SnowLuma/releases/latest （选 `SnowLuma-vX.Y.Z-win-x64.zip` 完整版） |
| 加速镜像 | 在 Release 资产链接前加 `https://ghfast.top/` |
| 手动 | 浏览器下载后放到本项目根目录，重跑 `一键部署-SnowLuma版.bat` |

## 2. 启动

先确认**桌面版 QQ 已登录**，然后双击 **`启动-SnowLuma版.bat`**：

- 先在新窗口拉起 SnowLuma 协议端（窗口标题「SnowLuma 协议端」）
- 约 10 秒后在本窗口启动业务框架 NoneBot
- 控制台出现 `Running on http://127.0.0.1:8081` 即业务端就绪

## 3. 登录账号（首次需扫码）

1. 浏览器打开 **http://127.0.0.1:5099**
2. 用启动日志里的初始账号密码登录（`admin` + 随机密码，**只显示一次**，记不住就重启 SnowLuma 重新生成）
3. 按引导「接入 QQ」：SnowLuma 会自动发现运行中的 `QQ.exe` 并注入 hook，弹出二维码
4. 扫码登录**目标账号**（本项目与老项目必须错开号，否则互踢）
5. 登录成功后，SnowLuma 会立即按配置连上业务框架

## 4. 验证

双击 **`自检-SnowLuma版.bat`**，看到这几行即为全通：

```
【3】端口与进程
[OK] SnowLuma WebUI（5099） 监听中
[OK] SnowLuma HTTP（3100） 监听中
[OK] 业务框架 NoneBot（8081） 监听中
【4】协议端日志
[OK] hook 注入成功，账号 <目标账号> 已登录
[OK] 已连上业务框架（ws://127.0.0.1:8081/onebot/v11/ws）
【5】业务框架
[OK] 账号 <目标账号> 已接入业务框架，群管功能生效
```

再用另一个 QQ 给该账号私聊发 `/ping`，有回复即完全打通。群内命令需目标群在 `qq-group-bot\config.json` 的 `managed_groups` 里。

## 5. 停止

双击 **`关闭-SnowLuma版.bat`**：只停本项目（协议端 + 业务框架），不会影响老项目。

若 SnowLuma 控制台窗口没关干净，直接关闭标题为「SnowLuma 协议端」的窗口即可。

## 6. 切换登录账号（脚本化）

> 一句话：把「在 5099 网页点卸载、再加载账号」变成一条命令。
> 走的是 SnowLuma 自己的 HTTP API（和网页同一条通道），**不是**改配置文件。

### 能脚本化 / 不能脚本化的边界

| 动作 | 能否脚本化 | 实现 |
|---|---|---|
| SnowLuma 卸载旧账号的 hook | ✅ | `POST /api/processes/{pid}/unload` |
| SnowLuma 加载目标账号 | ✅ | `POST /api/processes/{pid}/load` |
| 校正目标账号协议端配置（HTTP 3100 / WS 3001 / wsClient → 8081） | ✅ | 脚本按模板自动补齐或修正 |
| **QQ 客户端退出旧号、登录新号** | ❌ | 需要账号密码 + 手机验证；QQ 客户端没有稳定可用的命令行换号接口，**必须人工** |

### 用法

```
双击 切换账号.bat                    # 按提示输入目标 QQ 号 + WebUI 密码
切换账号.bat list                    # 只看当前有哪些账号、hook 是否加载

python deploy\snowluma_account.py list              # 同上
python deploy\snowluma_account.py list --raw        # 附带服务端原始 JSON（字段对不上时排障）
python deploy\snowluma_account.py switch 1000000001  # 切到目标账号
python deploy\snowluma_account.py unload 2000000002  # 只卸载某个账号（也支持按 PID）
```

密码来源：环境变量 `SNOWLUMA_WEBUI_PASSWORD`（自动化用），否则运行时交互输入，**不落盘**。

### 正确顺序

1. **人工**：桌面版 QQ 里登出旧号、登录目标号（SnowLuma 会自动发现新登录）
2. `切换账号.bat` 输入目标号 → 脚本自动卸载其它账号 hook、校正配置、重载目标
3. `自检-SnowLuma版.bat` 复核链路

### ⚠ 反面教材（已踩过的坑）

**直接复制 `SnowLuma\config\onebot_<新号>.json` 切号是不对的**：SnowLuma 会同时为两个账号建立 session，
两个 session 抢 **3100 / 3001** 端口，日志里刷一片 `EADDRINUSE`，状态会脏（一个号在跑、另一个号半死不活）。
必须走「先卸载、再加载」，也就是 `切换账号.bat` 做的两件事。

## 7. 排障对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| 自检报"未找到 SnowLuma 日志" | 协议端没起来 | 确认 `SnowLuma\launcher.bat` 存在，双击启动脚本；看 SnowLuma 窗口报错 |
| 日志里没有 `login detected` | hook 注入失败 | ①QQ 是否在运行并已登录 ②SnowLuma 与 QQ 是否同用户同权限 ③QQ 版本是否与 SnowLuma 对齐 |
| 有登录但 WS 未连上 | OneBot 配置没生效 | 检查 `SnowLuma\config\onebot_<目标账号>.json` 的 `wsClients` 是否为 `ws://127.0.0.1:8081/onebot/v11/ws`，改完重启 SnowLuma |
| 业务框架起不来、提示端口占用 | 8081 已被别的程序占用 | 改 `qq-group-bot\.env` 的 PORT 与 SnowLuma 配置里的 wsClient 地址（两处必须一致） |
| 群里发命令没反应 | 该群不在管理名单 | 在群里用 `/添加管理群` 或改 `qq-group-bot\config.json` 的 `managed_groups` |
| 同一个群收到两条回复 | 两个号都在该群且都在跑 | 正常现象（老项目也响应）；测试请换群或停掉一边 |
| 日志刷 `EADDRINUSE 127.0.0.1:3100/3001` | 两个 QQ 账号同时被接管，抢同一组端口 | 跑 `切换账号.bat`：卸载非目标账号 hook，只留一个号接管 |
| 命令没反应但私聊正常 | 群里缺 `/` 前缀 | 命令一律 `/命令` 形式（如 `/ping`、`/禁言 @某人 10`） |
| `切换账号.bat` 报"接口返回成功，但复核发现 hook 仍在加载" | SnowLuma 卸载未真正生效（日志里对应 `[Hook] unload verification failed: PID=xxx pipe still up`） | 再执行一次切换命令，或到 5099 网页上手动点卸载；确认 3100/3001 只被一个进程占 |
| 换了机器/拷了项目后 `一键部署-SnowLuma版.bat` 报依赖装不上 | 项目自带的 `venv\` 绑死了原机器的 Python 路径 | v1.2.0 起脚本会自动把坏 venv 改名为 `venv.machine-bound\` 并重建；若仍失败，手动改名后重跑 |
| SnowLuma 日志里一条群消息出现十几条 `get_group_member_info` | v1.2.0 之前的 `bot_is_admin` 缓存会被并发穿透 | 升级到 v1.2.0 后每群每 5 分钟只会查 1 次 |

## 8. 维护要点（每次动代码前后过一遍）

| 事项 | 做法 |
|---|---|
| 改业务插件（`qq-group-bot\`） | 改完必须重启业务框架才生效（关掉业务窗口，重跑 `启动-SnowLuma版.bat`） |
| 改完先自测 | `venv\Scripts\python.exe .workbuddy\test_admin_cache.py`、`.workbuddy\test_account_switch.py`（后者对着本地模拟服务跑，不会碰真实 SnowLuma，也不会写真实配置） |
| 跑业务前必须在 `qq-group-bot\` 目录 | `.env`（端口 8081、命令前缀）是相对 CWD 加载的；在项目根目录直接 `python qq-group-bot\bot.py` 会读不到 `.env` 而落到默认 8080，与老项目撞车。用启动 bat 就不会有这个问题 |
| QQ 版本 | SnowLuma 的 hook 按 QQ 版本对齐。**别把比对齐版本更新的 QQ 安装包放在项目里**（双击就升级 → hook 失效）；QQ 设置里关掉自动更新；`自检-SnowLuma版.bat` 会报"已下载的更新包" |
| 日志占用 | SnowLuma 默认输出 DEBUG，量较大（`runtime.json` 里 `logMaxTotalMb` / `logRetainDays` 控制轮转，默认 1GB / 7 天）；业务框架日志在 `logs\bot.log`，启动脚本每次是**追加**，长期跑要留意体积 |
| 发版 | 改完追加 `CHANGELOG.md` 条目 + 更新 `VERSION` + 打 annotated tag，一并推送（三件套缺一不可） |
| 敏感信息 | `部署配置.json`、`qq-group-bot\.env`、`config.json`、`.workbuddy\`、`SnowLuma\`、`venv\` 全部在 `.gitignore` 里；提交前确认它们没被 `git add -f` 拖进去 |

## 9. 服务器部署要点（后续迁移时用）

- 服务器若为 Windows，沿用本说明即可；若为 Linux，SnowLuma 选 `linux-x64` 包，业务框架用 `systemd`/`tmux` 常驻
- 无人值守跳过协议确认页：`set SNOWLUMA_ACCEPT_EULA=1` 与 `set SNOWLUMA_ACCEPT_PRIVACY=1`
- 早期试用的 AstrBot 那套已删除（业务框架统一用 NoneBot）
- 切换日流程：**先停老项目**（关它的看门狗窗口）→ 确认旧协议端进程退出 → 再启动本项目并登录
- 回滚：停本项目 → 双击老项目 `启动机器人.bat`
